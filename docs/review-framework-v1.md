# AI 系统审查框架 v1

## 1. 目标

这套框架用于审查自己拥有或已获明确授权的软件项目。核心顺序是：

```text
先定义正确结果 → 冻结现场 → 复现问题 → 证明根因 → 最小修复 → 独立验证 → 分层验收 → 可恢复交付
```

它不是漏洞利用手册，也不承诺自动找到所有 Bug。AI、测试和扫描器只提供证据的一部分，最终责任仍由项目负责人承担。

## 2. 四种结论

| 结论 | 含义 |
| --- | --- |
| `PASS` | 报告明确范围内的验收条件均有证据通过 |
| `FAIL` | 至少一个确认问题仍不满足验收条件 |
| `BLOCKED` | 缺权限、环境、数据或外部状态，暂时不能继续 |
| `NOT_TESTABLE` | 当前合法范围内没有可执行的验证路径 |

结论必须带范围。不能把“局部测试 PASS”写成“整个系统 PASS”。

单个步骤或验收层还可以使用 `NOT_APPLICABLE`，表示该层本来就不属于任务合同，例如纯命令行项目没有浏览器层。它与 `NOT_TESTABLE` 不同：后者表示本应判断，但当前没有合法可行的验证路径。总体结论仍使用上表四种。

多个结果同时出现时，总体结论按以下顺序归并：

1. 任一适用验收条件确认失败：总体 `FAIL`，并另列仍存在的 `BLOCKED` 与 `NOT_TESTABLE` 项；
2. 没有失败，但任一适用条件受阻：总体 `BLOCKED`；
3. 没有失败或受阻，但任一必需条件无法测试：总体 `NOT_TESTABLE`；
4. 所有适用条件都有证据通过：总体 `PASS`。

`NOT_APPLICABLE` 不参与总体归并，但每项都要说明为何不属于合同范围。

## 3. 八条硬原则

1. **完成必须附证据。** “AI 说完成”“代码能运行”“测试全绿”都不是单独的完成标准。
2. **风险决定深度。** 不用文件数量或改动行数代替权限、资金、数据、生产影响和可恢复性判断。
3. **默认先只读。** 先确认问题，项目负责人授权后才修复；生产诊断默认只读。
4. **发现、验证、验收分开。** AI 负责扩大检查面，确定性工具负责证伪或确认，真实产品路径和人类负责最终用途。
5. **默认单一修改者。** 独立复查者不修改实现，验收者不改测试来迁就结果。
6. **发现只是候选。** 没有对象、触发条件、影响和证据的“可能有风险”不能算确认问题。
7. **验收层不能互相代替。** 单元测试不证明浏览器，管理员不证明普通角色，技术发布不证明业务正确。
8. **必须可停止、可恢复。** 保护用户已有改动，记录回滚对象；需要扩大权限、费用或范围时立即停下。

## 4. 风险分级

| 等级 | 典型任务 | 最低审查门 | 人类责任 |
| --- | --- | --- | --- |
| R0 | 文档、样式、局部无状态脚本 | 差异、自检、适用的 lint/build/smoke | 快速抽查 |
| R1 | 普通功能、一般 Bug、单模块重构 | 复现、回归、相关全量测试、独立复查、手动抽查 | 确认合同与结果 |
| R2 | 登录、权限、支付、财务、隐私、导入导出、跨模块数据 | 冻结正确结果、回归与安全双视角、真实角色、恢复验证 | 业务或数据负责人明确批准 |
| R3 | 生产写入、迁移、删除、不可逆操作、共享基础设施 | 明确授权、完整备份、真实恢复演练、不可变制品、逐步发布、精确回滚 | 每个写入门都由人批准 |

升级规则：不确定时升一级。涉及秘密、权限、资金、个人数据、生产环境或难以恢复的动作时，不得按 R0 处理。

## 5. 角色

| 角色 | 可以做 | 默认不能做 | 主要输出 |
| --- | --- | --- | --- |
| Owner | 定义目标、范围、授权和业务正确性 | 把最终责任交给模型 | 任务合同、是否接受结果 |
| Writer | 诊断并做最小修复 | 自称独立审查通过 | 差异、测试、实现证据 |
| Reviewer | 冷上下文检查合同、差异、测试和影响面 | 修改代码、替 Writer 辩护 | 带证据的候选发现 |
| Security Reviewer | 按实际威胁面做安全检查 | 未授权攻击、批量自动修复 | 已确认、误报、待验证项 |
| Verifier | 按合同做黑盒或真实路径验收 | 改实现、改验收条件 | `pass/fail/blocked/not-testable`；不适用层可写 `not-applicable` |

R0 可以由 Writer 自检，但报告必须注明“不是独立审查”。R1 及以上默认分开。

## 6. 开始前预检

正式计时或修改前先检查：

- 项目自己的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`、`.github/copilot-instructions.md`、`CONTRIBUTING.md`、测试说明和更具体规则；这些规则可以收紧做法，但不能扩大 Owner 给出的权限；
- Git 分支、commit、已有修改和所有未跟踪文件；
- 测试运行器、依赖、浏览器、数据库或必需二进制是否真的可用；
- 哪些操作会联网、收费、登录、读真实数据或产生业务写入；
- 只读级别是“纯静态读取”，还是允许执行会产生缓存或临时文件的指定本地诊断命令；
- 证据目录不会保存秘密，日志和截图有脱敏办法；
- Writer、Reviewer、Verifier 的职责和交接物已确定。

缺失项应在开始前写为 `BLOCKED` 或明确降级范围，不能等到最后再把未执行项算作通过。本来就不属于合同范围的层写为 `NOT_APPLICABLE` 并说明理由。

## 7. Gate 0—10：共 11 道门

### Gate 0：任务合同

填写 [任务合同](../templates/review-contract.md)：

- 唯一要回答的问题；
- 范围与明确非范围；
- 权威需求和正确结果；
- 验收条件；
- 风险等级；
- 允许和禁止动作；
- 网络、账号、费用、生产边界；
- 允许的本地诊断命令及其缓存、临时文件等副作用；
- 停止条件。

合同不清楚时可以只做纯静态信息收集，不能开始修改，也不能擅自运行会写缓存、临时文件、数据库或外部状态的命令。

### Gate 1：冻结基线

- 记录仓库、分支、commit、Git dirty 状态和运行环境。
- 把已跟踪修改和未跟踪文件都列入清单，不清理、不覆盖、不重置用户改动。
- 保存失败截图、原始日志、最小输入、关键输出哈希和已知正常结果。
- 固定测试命令、工具版本和配置；不能稳定复现时写清观察标准。

### Gate 2：理解系统和影响范围

- 先读本地规则、架构、接口和数据不变量。
- 画最小模块或数据流，找出共享写入者、权限边界和回滚对象。
- 从输入到输出跟踪一条真实路径，不只看报错所在文件。
- 大型仓库可以用图谱或搜索工具辅助导航，但结论必须回到源码、配置或运行证据。

### Gate 3：只诊断，不修复

在合同允许的只读级别内，使用 [Bug 诊断与修复模板](../templates/bug-diagnosis-and-fix.md)：

1. 稳定复现；
2. 缩小输入；
3. 找到第一个出现错误的边界；
4. 建立假设表；
5. 逐条用最小实验证伪；
6. 有根因证据后才进入修复。

同一方向连续三轮没有新证据时停止，冻结现场并换冷上下文或请求新信息，不能无限试改。

### Gate 4：最小修复

- 先准备一个能证明“修复前失败”的测试或正确结果对照。
- 一次只处理一个确认问题，并保持单一 Writer。
- 不借机大重构、升级依赖、修改验收条件或处理无关告警。
- 每次修复都要知道怎样单独撤销。

### Gate 5：确定性验证

按适用顺序保留命令、版本、退出码和结果：

1. 修复前失败证据；
2. 聚焦回归测试；
3. 正确结果或差异对照；
4. 相关全量测试；
5. type、lint、build、格式和迁移检查；
6. 按风险选择密钥、依赖、静态或动态安全扫描。

透明测试桩只能证明对应单元测试，不能被写成真实下载、网络、数据库或生产运行通过。

### Gate 6：独立 Review

Reviewer 使用新的上下文，只接收冻结合同、基线、完整差异、未跟踪文件、验证证据和必要代码。

每条发现至少包含：

- 具体对象和位置；
- 触发条件；
- 预期与实际；
- 影响；
- 当前证据；
- 建议的最小验证方法。

AI 或扫描器的输出一律先进入 `candidate`，不能直接批量自动修复。

### Gate 7：黑盒与真实路径验收

按项目选择：

- UI：真实浏览器、目标屏幕宽度、键盘操作，以及加载、空、错误、成功状态；
- 权限：用实际目标角色分别验收，管理员通过不能代替员工或客户；
- 数据：同一筛选范围下核对页面、接口、导出和数据库不变量；
- 外部集成：只用明确授权的测试账号或沙箱，在费用或业务写入前停止确认。

Verifier 对每个验收条件返回 `pass / fail / blocked / not-testable`；对本来不属于合同范围的验收层可写 `not-applicable`。每项都要附证据或缺口，总体结论按第 2 节规则归并。

### Gate 8：安全专项

根据实际威胁面选择最小集合，例如：

- 秘密泄漏检查；
- 依赖漏洞检查；
- 静态代码检查；
- Web 被动扫描；
- 权限、越权、输入验证、敏感数据和审计日志检查。

主动扫描、漏洞利用、真实数据读取或外部系统写入必须有单独授权和隔离范围。安全工具的输出仍先算候选问题。

### Gate 9：发布与恢复

- 固定发布制品、版本、文件清单和确切回滚目标。
- 备份不只要“存在”，还要验证能读取；R2/R3 应在隔离环境证明能恢复。
- 定义健康、错误率、延迟、业务不变量和自动停止信号。
- 逐步发布，生产验收先只读，所有写入对象和数量可核对。
- 技术发布成功不等于真实用户或业务已经接受。

没有发布任务时，将本门标记为 `NOT_APPLICABLE`，不要虚构发布证据。

### Gate 10：关闭与学习

填写 [最终报告](../templates/review-report.md)：

- 范围和基线；
- 已确认问题与误报；
- 各验收层状态；
- 未决风险；
- 回滚方法；
- 下一步唯一动作。

只有已验证的问题才能关闭。项目负责人可以接受风险，但必须留下责任人、理由和期限。

## 8. 问题生命周期

正常路径：

```text
candidate → confirmed → fixing → fixed_unverified → verified → accepted → closed
```

旁路状态：

- `false_positive`：已有反证，记录为什么不成立；
- `dismissed`：Owner 明确接受风险，记录负责人和期限；
- `blocked`：缺权限、环境、数据或外部条件，记录解除条件；
- `not-testable`：合法范围内没有验证路径，绝不能写成 PASS。

`NOT_APPLICABLE` 是步骤或验收层状态，不是一个问题的生命周期状态，因此不写进问题账本。

统一字段见 [问题账本](../templates/finding-ledger.md)。

## 9. 严重度

| 等级 | 建议含义 |
| --- | --- |
| P0 | 正在或极可能造成严重资金、数据、安全或大范围不可恢复损失，需要立即停止 |
| P1 | 高影响、容易触发或影响关键流程，应优先处理 |
| P2 | 明确缺陷但影响有限、有绕行方法或不在关键路径 |
| P3 | 低影响问题、边界改善或维护风险 |

严重度描述影响，处理顺序还要结合发生概率、恢复成本和业务时间窗口。

## 10. 验收层必须分开

最终报告至少分开写：

| 层级 | 典型证据 |
| --- | --- |
| 静态检查 | type、lint、build、格式、静态扫描 |
| 自动测试 | 聚焦回归、相关全量测试 |
| 差异与正确结果 | 修复前后对照、数据不变量、冻结样本 |
| 独立 Review | 冷上下文复查结论与误报反证 |
| 浏览器与角色 | 真实页面、真实目标角色、关键状态 |
| 运行环境 | 实际服务、依赖、数据库、网络集成 |
| 生产发布 | 制品、健康、监控、回滚、只读核对 |
| 人工与业务 | 负责人对用途、内容和业务结果的接受 |

任一层的 PASS 都不能自动填充其他层。

## 11. 可选工具原则

先用项目已有的 Git、测试、lint、typecheck、build 和迁移检查。再按实际风险考虑：

- 秘密检查；
- 依赖漏洞检查；
- 静态代码分析；
- Web 被动扫描；
- 浏览器自动化；
- 大型仓库导航和代码图谱；
- AI Review 编排。

工具不是越多越好。只有它在真实项目中能重复降低漏报、误报、耗时或恢复风险，且没有明显增加代码外传、费用、权限和维护成本，才适合成为默认工具。

## 12. 建议证据目录

```text
audit/YYYY-MM-DD-short-name/
  review-contract.md
  baseline.md
  finding-ledger.md
  evidence/
  review-report.md
```

证据可以放在项目外部。任何位置都不能保存密码、令牌、Cookie、私钥、完整连接串或不必要的真实个人数据。

## 13. 最小执行方式

- R0：合同简版 → 基线 → 差异与适用测试 → 自检说明 → 报告。
- R1：完整复现 → 最小修复 → 回归与相关全量 → 独立 Review → 黑盒抽查 → 报告。
- R2：R1 全部内容 → 安全双视角 → 真实角色与数据不变量 → 恢复验证 → 负责人批准。
- R3：R2 全部内容 → 单独写入授权 → 完整备份与恢复演练 → 不可变制品 → 逐步发布 → 生产只读核对 → 人工批准。
